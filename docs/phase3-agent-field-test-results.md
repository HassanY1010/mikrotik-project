## 3. الأخطاء الحرجة المكتشفة أثناء الاختبار الحي والإصلاحات المنفذة

أثبت الاختبار التكاملي الحي قيمته الحاسمة عبر استكشاف أخطاء جوهرية كانت تمر دون رصد في اختبارات الوحدة (Unit Mocks) بسبب عزل الـ Controllers عن سياق الـ Global Pipeline:

### 3.1 الخطأ الحرج الأول: حظر الـ Global `JwtAuthGuard` لنقاط نهاية الوكيل
* **طبيعة المشكلة:**
  - في [`app.module.ts`](file:///e:/microTik_project/apps/api/src/app.module.ts)، تم تسجيل `JwtAuthGuard` كـ Global Guard (`APP_GUARD`)، مما يعني أن أي مسار في التطبيق يطلب تلقائياً User JWT في ترويسة `Authorization` إلا إذا وُسم بالمزخرف `@Public()`.
  - كانت مسارات الوكيل (`/agent/pair`، `/agent/heartbeat`، `/agent/validate`، `/agent/commands/:id/result`) تفتقر إلى مزخرف `@Public()`.
  - عند محاولة الوكيل الإقران أو إرسال النبضات عبر HTTP الحقيقي، كان الحارس يعترض الطلب ويعيد `401 Unauthorized` فوراً قبل أن يصل الطلب إلى الـ Controller!
* **الإصلاح المنفذ:**
  - تم استيراد وتطبيق مزخرف `@Public()` على المسارات الأربعة في [`apps/api/src/modules/agent/agent.controller.ts`](file:///e:/microTik_project/apps/api/src/modules/agent/agent.controller.ts). تقوم هذه المسارات بالتحقق الذاتي من رموز الإقران أو توكنات الوكيل الخاصة بها دون الحاجة لـ User JWT.

### 3.2 الخطأ الحرج الثاني: تغليف استجابة النبضات بواسطة `TransformInterceptor`
* **طبيعة المشكلة:**
  - يعتمد النظام محول الاستجابة الشامل [`TransformInterceptor`](file:///e:/microTik_project/apps/api/src/core/interceptors/transform.interceptor.ts) الذي يقوم بتغليف أي استجابة لا تحتوي على خاصية `success: boolean` في قالب `{ success: true, data: ... }`.
  - كانت دالة `processHeartbeat` تعيد كائناً بصيغة `{ status: 'ACK', serverTime: ..., pendingCommands: [...] }` دون حقل `success`.
  - قام المحول بتغليفها في `{ success: true, data: { status: 'ACK', ... } }`، مما جعل الوكيل يستقبل `res.status` و `res.pendingCommands` بقيمة `undefined` لغياب فك التغليف!
* **الإصلاح المنفذ:**
  - عُدّل [`api-client.ts`](file:///e:/microTik_project/apps/agent/src/transport/api-client.ts) لفك تغليف أي استجابة تحتوي على حقل `data` تلقائياً (`res?.data ?? res`).
  - عُدّل [`heartbeat.dto.ts`](file:///e:/microTik_project/apps/api/src/modules/agent/dto/heartbeat.dto.ts) و [`agent.service.ts`](file:///e:/microTik_project/apps/api/src/modules/agent/agent.service.ts) لتضمين `success: true` صراحة، مما يضمن التوافق المزدوج.

### 3.3 الخطأ الحرج الثالث: إعادة المحاولة غير الضرورية عند أخطاء المصادقة (401)
* **طبيعة المشكلة:**
  - كان تابع `executeWithRetry` في `api-client.ts` يعامل أخطاء 401 كأخطاء عامة يُعاد طلبها 5 مرات مع تأخير أسي، مما كان يستهلك 30 ثانية دون جدوى عند رفض توكن غير صالح أو محاولة إقران فاشلة.
* **الإصلاح المنفذ:**
  - إنشاء فئة استثناء خاصة `AuthenticationError` وإضافتها لقائمة الاستثناءات التي تفشل فوراً دون إعادة محاولة في [`api-client.ts`](file:///e:/microTik_project/apps/agent/src/transport/api-client.ts).

## 5. مراجعة أمان وكفاءة Windows Agent

### 5.1 آلية التشغيل التلقائي (Scheduled Task vs Windows Service)
- **التوصيف الدقيق:** يستخدم المثبت أداة **Windows Task Scheduler** (`schtasks.exe`) بنمط `/sc ONLOGON /rl HIGHEST /f`.
- **سلوك التشغيل:**
  - **يبدأ تلقائياً فقط بعد تسجيل دخول المستخدم (User Logon) المسجل على الجهاز.**
  - **لا يعمل قبل تسجيل الدخول** ولا يستمر في الخلفية إذا قام المستخدم بتسجيل الخروج الكامل (Log off).
  - هذا السلوك مطلوب أمنياً ليتوافق 100% مع نطاق تشفير **Windows DPAPI `CurrentUser`** ومسار `%APPDATA%` الخاص بالمستخدم.
  - لا يُدّعى نهائياً أن الوكيل يعمل كخدمة Windows Service حقيقية بدون وسيط (مثل NSSM أو WinSW).

### 5.2 حماية بيانات الاعتماد على Windows
- **التشفير الأصيل:** يعتمد الوكيل حصرياً على واجهة Windows Data Protection API (DPAPI):
  `[System.Security.Cryptography.ProtectedData]::Protect(..., CurrentUser)`
  المربوطة بـ TPM ومفتاح LSA الخاص بنظام التشغيل.
- **الـ Fallback:** في حال فشل DPAPI أو العمل على غير ويندوز، يُشتق مفتاح AES-256-GCM في الذاكرة عبر بصمة العتاد. **ولا يُخزن أي مفتاح بجانب الملف المشفر على القرص نهائياً.**
- **تقييد الأذونات:** يتم تطبيق أمر `icacls` لحصر صلاحيات القراءة والكتابة بمستخدم Windows المشغل فقط.

### 5.3 سلوك الوكيل عند انقطاع الاتصال ونوم الخادم (Render Sleep)
- تم تزويد الوكيل بمهلة اتصال افتراضية **60 ثانية** مع 5 محاولات إعادة اتصال وتأخير أسي عشوائي (Exponential Backoff with Jitter).
- في حال نوم خادم Render المجاني، تستغرق الاستجابة بين 45-75 ثانية؛ تم اختبار استمرار الوكيل في انتظار الخادم واستعادة الاتصال فور استيقاظه دون انهيار العملية.

### 5.4 حالة التوزيع والتجميع المستقل (Standalone Executable)
- يعمل الوكيل حالياً عبر نصوص التشغيل [`sudafi-agent.cmd`](file:///e:/microTik_project/apps/agent/sudafi-agent.cmd) و [`sudafi-agent.ps1`](file:///e:/microTik_project/apps/agent/sudafi-agent.ps1) بالاعتماد على بيئة Node.js المثبتة في النظام.
- **لا يوجد ملف `.exe` مجمّع ومستقل حتى الآن**، وتم استبعاد ادعاء ذلك لالتزام الأمانة التقنية.
