## 2. دراسة وتقييم وسيط النقل: WebSocket مقابل HTTPS Polling على استضافة Render المجانية

### أ) دراسة محددات باقة Render المجانية (Render Free Web Service)
- **دورة النوم والخمول (Spindown after 15 min):** تدخل الحاوية المجانية في وضع النوم بعد 15 دقيقة من خمول حركة الـ HTTP الواردة.
- **مهلة الاتصال الخامل لبوابات Cloudflare/Render:** بوابات البروكسي تُسقط أي اتصال TCP/WebSocket يظل خاملاً لأكثر من 55–100 ثانية.
- **سلوك اتصالات WebSocket الدائمة:**
  - عند نوم الحاوية أو إعادة تشغيلها أو إعادة نشرها، تنقطع كافة اتصالات WebSocket المفتوحة بـ `1006 Abnormal Closure`.
  - عدم استخدام Redis (وفق القيد الصارم: "لا تضف Redis أو أي خدمة مدفوعة") يجعل أي طابور أوامر مرتبط بذاكرة عملية WebSocket عرضة للضياع التام عند إعادة تشغيل الحاوية.
  - شبكات Starlink وCGNAT وشبكات الهواتف المحمولة تعاني من تقلبات مفاجئة تُسقط جلسات TCP الطويلة وتتطلب إعادة مصادقة مكلفة.

### ب) تقييم بروتوكول الاستطلاع ونبضات HTTPS (HTTPS Heartbeat & Command Dispatch)
- **الملاءمة التامة لـ Render المجاني:**
  - كل طلب نبضة (`POST /api/v1/agent/heartbeat`) هو طلب HTTPS قياسي يصل إلى بوابة البروكسي. إذا كانت الحاوية في وضع النوم، فإن وصول طلب الـ Heartbeat **يقوم بإيقاظ الحاوية تلقائياً (Cold Start)** دون الحاجة لأي مشغل خارجي.
  - الحاوية عديمة الحالة (Stateless): لا تعتمد على اتصالات TCP ثابتة في الذاكرة.
  - **طابور أوامر مستمر وموثوق (Persistent RPC Queue):** يتم تخزين الأوامر في قاعدة البيانات برمز ذرية فريد (`operationId`)، وتُحمّل الأوامر المعلقة ضمن استجابة النبضة الدورية.
  - لا حاجة لـ Redis أو اشتراكات مدفوعة: تعتمد على PostgreSQL وExpress فقط.
  - حماية تامة ضد انقطاعات Starlink: في حال فشل طلب HTTPS نتيجة انقطاع شبكة مؤقت، يُعيد الوكيل المحاولة تلقائياً بـ Exponential Backoff دون تلف حالة المقبس.

### ج) القرار المعماري المعتمد
تم اعتماد **HTTPS Heartbeat & Command Dispatch Protocol** كناقل أساسي متين ومقاوم لانقطاعات الإنترنت ونوم خوادم Render، مع تصميم مهيكل يسمح مستقبلاً بربط WebSocket Gateway كطبقة نقل ثانوية عند الترقية إلى خوادم دائمة التشغيل دون المساس بطبقة منطق الأوامر.

## 3. تفاصيل التصميم والتنفيذ البرمجي

### أ) بروتوكول النبضات وحالة الوكيل (Heartbeat & Presence)
1. **نقطة النهاية:** `POST /api/v1/agent/heartbeat`
2. **المصادقة:** يتحقق الخادم من `rawToken` المرسل في ترويسة `Authorization: Bearer <token>` أو `x-agent-token`.
   - يتم اشتقاق الـ Hash ومطابقته مع `device_agents.tokenHash`.
   - يتم التحقق من أن الوكيل غير ملغى (`status != REVOKED`)، وأن الراوتر والمستأجر نشطان وغير محذوفين.
3. **تحديث الحضور:**
   - يُحدّث `lastPingAt = now` و `status = ONLINE` وعنوان الـ IP الحقيقي المعتمد عبر `trust proxy`.
   - يتم استقبال مقاييس اختيارية (`metrics`): زمن التشغيل، استهلاك المعالج، الذاكرة المتاحة، وزمن استجابة الراوتر المحلي `routerPingMs`.
4. **كشف الانقطاع والتحول إلى `OFFLINE`:**
   - **المهلة المحددة:** النبضة تُرسل كل 25 ثانية (`HEARTBEAT_INTERVAL_MS = 25000`)، ومهلة الانقطاع محددة بـ 60 ثانية (`HEARTBEAT_TIMEOUT_MS = 60000`).
   - **آلية مزدوجة لكشف الانقطاع:**
     1. **كشف كسول عند الاستعلام (Lazy on-query):** عند طلب حالة الوكيل عبر `GET /devices/:id/agent`، إذا كان الوكيل `ONLINE` ومضى أكثر من 60 ثانية على آخر نبضة، يُحدث تلقائياً إلى `OFFLINE` في قاعدة البيانات.
     2. **ماسح دوري غير حاجب (Background Sweeper):** مهمة دورية غير حاجبة (`this.sweepInterval.unref()`) تعمل كل 30 ثانية لتحديث أي وكلاء انقطعت نبضاتهم إلى `OFFLINE`.

### ب) بروتوكول الأوامر المقيدة ومنع التكرار (Typed RPC & Idempotency)
1. **حظر الأوامر العامة نهائياً:**
   يُمنع كلياً إرسال أوامر CLI مفتوحة أو نصوص شل عامة. أي أمر لا ينتمي إلى قائمة الأنواع البيضاء المعتمدة يُرفض فوراً بـ `400 Bad Request`.
2. **قائمة الأوامر التطبيقية المعتمدة (`AgentCommandType`):**
   - `system.router.health`: فحص صحة واستجابة الراوتر.
   - `hotspot.user.batch_add`: إضافة دفعة كروت هوتسبوت (محددة بـ `batchNumber` ومصفوفة `users`).
   - `hotspot.user.remove`: حذف مستخدم هوتسبوت محدد.
   - `hotspot.user.verify_batch`: مطابقة والتحقق من كروت الدفعة.
   - `hotspot.session.list`: جلب الجلسات النشطة.
3. **منع التكرار والذرية (Idempotency via `operationId`):**
   - كل أمر يُرسل مع معرّف `operationId` فريد بصيغة UUIDv4.
   - في حال إعادة إرسال نفس الأمر بنفس الـ `operationId` لنفس الراوتر، يُعيد الخادم السجل السابق دون تكرار إنشاء الأمر.
   - في حال استخدام نفس الـ `operationId` لراوتر آخر، يُلقي الخادم `409 ConflictException`.
4. **تسليم الأوامر وتأكيد التنفيذ:**
   - تُسلّم الأوامر المعلقة (`PENDING`) ضمن استجابة النبضة، وتتحول فورياً إلى `DISPATCHED`.
   - يقوم الوكيل بإرسال نتيجة التنفيذ إلى `POST /api/v1/agent/commands/:id/result`.
   - إذا تم إرسال نتيجة لأمر مكتمل مسبقاً، يتعامل الخادم بذرية ويُعيد نجاحاً مع رسالة `Command result already recorded (idempotent)` دون تكرار التعديل.

### ج) أمان السجلات وعزل المستأجرين
- **حظر طباعة الأسرار والتوكنات:** السجلات لا تطبع توكنات الوكلاء أو كلمات مرور الراوترات أو تفاصيل الحمولات الحساسة؛ يُكتفى بالمعرفات العامة والرموز المشفرة.
- **عزل المستأجرين:** يُمنع أي مستأجر من جدولة أوامر لراوتر مستأجر آخر (`403 Forbidden`)، ويُمنع أي وكيل من الوصول لأوامر راوتر آخر.
