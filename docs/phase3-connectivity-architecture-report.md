## 1. وصف البنية الحالية المثبتة من فحص الكود

بناءً على الفحص الشامل للشيفرة المصدرية الحالية في `apps/api/src/core/mikrotik/` و`apps/api/src/modules/devices/` و`apps/api/src/modules/cards/`:

### 1.1. آلية الاتصال وتدفق البيانات الفعلي
1. **طراز العميل والاتصال المباشر:**
   - تستخدم المنظومة واجهتي اتصال:
     - `RouterOsApiClient` (`routeros-api.client.ts`): تعتمد بروتوكول المقابس الخام (Raw TCP Sockets عبر `net.createConnection` أو `tls.connect`) على المنفذ `8728` (أو `8729` لـ SSL) لتنفيذ أوامر RouterOS الثنائية (Sentence/Word Protocol).
     - `RouterOsRestClient` (`routeros-rest.client.ts`): تعتمد بروتوكول HTTP/HTTPS عبر `fetch` على المنفذ `443` أو `80` لمسار `/rest` المدعوم حصراً في RouterOS v7.1+.
   - يتم إنشاء العميل عبر مصنع مركزي `MikrotikClientFactory` (`mikrotik-client.factory.ts`) مع كاش للاتصالات النشطة لمدة 3 دقائق (`IDLE_TIMEOUT_MS = 180000ms`).
2. **تخزين وتشفير بيانات الاعتماد:**
   - تُخزن بيانات الراوتر في جدول `mikrotik_devices` في PostgreSQL:
     - الحقول: `host`, `apiPort`, `restPort`, `useSsl`, `username`, `passwordEncrypted`, `iv`, `authTag`, `rosVersion`.
     - التشفير: تشفير قوي في وضع السكون باستخدام `AES-256-GCM` عبر خدمة `EncryptionService` مع مفتاح سري بيئي `ENCRYPTION_KEY`، مع حفظ الـ IV وAuthentication Tag بصيغة Hexadecimal.
3. **المهلات وإعادة المحاولة:**
   - مهلة الاتصال الفوري: `timeoutMs: 2500ms` إلى `3000ms` في المصنع، و`8000ms` في فحص التشخيص `testConnection`.
   - عند فشل الاتصال، يتم رصد الخطأ وتصنيفه (`NETWORK`, `PORT`, `AUTH`, `TLS`) وتحديث حقل `isOnline = false` و`lastError = rawError` في قاعدة البيانات.
   - في توليد الكروت (`cards.service.ts`): يتم إنشاء الكروت أولاً في قاعدة البيانات بحالة `PENDING`، وإذا كان الراوتر متصلاً (`device.isOnline: true`) يتم إرسال المستخدمين تباعاً عبر `client.createHotspotUser`. وفي حال فشل الاتصال، تُعلّم الكروت بحالة `FAILED` أو `PENDING_OFFLINE` لتتم مزامنتها لاحقاً.

## 2. نقاط الضعف والعوائق الفعلية (Root Cause Analysis)

### 2.1. لماذا يفشل الاتصال بعنوان محلي مثل `192.168.88.1` من خادم سحابي؟
- **طبيعة العناوين الخاصة (RFC 1918 Private IP):** العناوين `192.168.88.0/24` و`10.0.0.0/8` و`172.16.0.0/12` هي نطاقات محلية مخصصة للشبكات الداخلية (LANs). لا يمكن توجيهها (Non-routable) عبر الإنترنت العام.
- **عزلة حاويات Render (Cloud Sandbox):**
  - يعمل خادم الـ API على منصة Render (`https://mikrotik-api-yn0e.onrender.com`) كحاوية Docker سحابية داخل شبكة Render السحابية (AWS/GCP).
  - عندما ينفذ كود Node.js:
    ```typescript
    net.createConnection({ host: '192.168.88.1', port: 8728 })
    ```
    يبحث نظام التشغيل في جدول التوجيه الداخلي للحاوية، ولا يجد أي مسار للشبكة المحلية الخاصة بالعميل المتواجد في السودان أو أي دولة أخرى، فيفشل الاتصال فوراً إما بانتهاء المهلة (`ETIMEDOUT`) أو رفض الشبكة (`ENETUNREACH` / `EHOSTUNREACH`).

### 2.2. عائق شبكات Starlink ومزودي الاتصالات (CGNAT Barrier)
- **Carrier-Grade NAT (CGNAT):**
  - تستخدم Starlink وشبكات الهاتف المحمول في السودان (Zain, MTN, Sudani, Canar) تقنية CGNAT في نطاق `100.64.0.0/10`.
  - يشترك آلاف المستخدمين في عنوان IPv4 عام خارجي واحد، والراوتر لا يملك Public IP خاصاً به.
  - جدران الحماية لدى مزودي الإنترنت وStarlink تمنع قطعياً أي اتصالات واردة (Inbound Traffic) موجهة نحو راوتر العميل من الإنترنت العام.
  - حتى لو تم استخدام خدمات Dynamic DNS (مثل `*.sn.mynetname.net` الخاصة بميكروتك)، فإن العنوان الذي يُحل هو عنوان بوابة المزود وليس منفذاً مفتوحاً نحو الراوتر.

### 2.3. مخاطر تعريض منافذ الراوتر للإنترنت المفتوح (Security Catastrophe)
- حتى في الحالات النادرة التي يملك فيها العميل Public IP حقيقي (Static/Dynamic)، فإن فتح منفذ `8728` (RouterOS API) أو `443` على الإنترنت العام:
  - يعرض الراوتر فورياً لهجمات التخمين الآلية (Brute Force) وقواميس كلمات المرور.
  - يستهدف الراوتر بالبوتات العالمية وهجمات حرمان الخدمة (DDoS) وبرمجيات التعدين الخبيثة (مثل Hajime وMeris).
  - يخرق معايير الأمان وعزل بيانات المستأجرين؛ فإذا تسرب عنوان IP، يمكن استهدافه مباشرة.

### 2.4. قيود منصة الاستضافة Render.com
- تعمل خوادم Render كـ **Web Services** قياسية:
  - تدعم فقط حركة المرور الواردة عبر HTTP/HTTPS على المنفذين `80` و`443` عبر وكيل عكسي (Reverse Proxy).
  - **لا تتيح فتح منافذ UDP أو TCP مخصصة واردة** (مثل منفذ WireGuard `51820/UDP` أو SSTP `443/TCP` المباشر).
  - حاويات Render **لا تملك امتيازات Linux الجذرية (`CAP_NET_ADMIN`) ولا وصولاً إلى أجهزة النفق `/dev/net/tun`**، مما يعني أنه **من المستحيل تشغيل خادم VPN كامل (WireGuard Server أو OpenVPN Server) داخل خدمة Render Web Service مباشرة**.

## 4. الحل المعماري الموصى به (The Recommended Architecture)

بعد التحليل الدقيق لقيود الاستضافة على Render، وطبيعة أجهزة ميكروتك المنتشرة في السودان (حيث نسبة كبيرة منها هي أجهزة RouterOS v6 مثل hAP lite وRB750r2 وRB951 ذات سعة تخزين 16MB ولا تدعم WireGuard أو الحاويات)، نوصي بـ:

### الحل الهجين ذو المستويين (Two-Tier Hybrid Architecture)

```
[ Tier 1: Production Cloud (Render.com + Supabase) ]
                      ▲
                      │  Persistent WSS (Outbound over TLS 443)
                      ▼
[ Tier 2 Option A: Lightweight LAN Relay Agent ] (الخيار الأسهل والأنسب للجميع)
   - يعمل على جهاز محلي (كمبيوتر الكاشير / نقطة البيع / أو مدمج في تطبيق Flutter للديسكتوب)
   - يتصل بالـ API سحابياً عبر WebSocket مؤمن
   - يتخاطب محلياً مع راوتر ميكروتك (192.168.88.1:8728) بدون إنترنت عام على الراوتر
   - يدعم RouterOS v6 وRouterOS v7 بلا استثناء وبلا تكلفة بنية إضافية

                      --- أو بدلاً من ذلك ---

[ Tier 2 Option B: Managed Gateway VPS (SSTP & WireGuard Hub) ] (للاتصال المستقل 24/7)
   - خادم Linux VPS مخصص ومؤمن (Hetzner بـ $4/شهر)
   - يشغل WireGuard لراوترات RouterOS v7، وخادم SSTP لراوترات RouterOS v6
   - يقوم الراوتر بإنشاء نفق صادر نحو الـ VPS، والـ API يتصل بالراوتر عبر نفق VPN المعزول
```

### أسباب اختيار هذا الحل الهجين:
1. **العمل الفوري مع Render الحالية:** لا يتطلب تعديل بيئة Render أو البحث عن مزودين يدعمون UDP للـ API.
2. **تخطي CGNAT وStarlink بنسبة 100%:** الاتصالات في كلا الخيارين صاعدة وصادرة (Outbound) من بيئة العميل، فلا تتأثر بالحجب ولا تحتاج أي Public IP.
3. **دعم 100% من أجهزة ميكروتك (v6 وv7):** حل معضلة الأجهزة الشائعة التي لا تدعم WireGuard.
4. **أمان معزول بالكامل (Zero Trust):**
   - راوتر العميل لا ينكشف للإنترنت.
   - لكل مستأجر هوية وتشفير منفصل.
   - حتى لو انقطعت الكهرباء أو تغير الـ IP الخارجي للراوتر مئات المرات، يعاد الاتصال تلقائياً دون تدخل بشري.

## 6. متطلبات الأمان والتصميم المحكم (Security Specification)

لضمان حماية المنصة والعملاء، يجب أن يتضمن التصميم القواعد التالية:

1. **عزل المستأجرين (Tenant Isolation):**
   - في خيار الوكيل (Agent): مصادقة كل وكيل عبر `AgentToken` مرتبط حصراً بـ `tenantId`. لا يمكن للوكيل استلام أو تنفيذ أي مهمة لا تخص مستأجره.
   - في خيار الـ VPS Hub: تقسيم شبكة الـ VPN إلى شبكات فرعية معزولة (`/30` لكل مستأجر، أو عزل كامل عبر `iptables -A FORWARD -s 10.100.0.0/16 -d 10.100.0.0/16 -j DROP`).
2. **حماية بيانات اعتماد الراوتر:**
   - استمرار تشفير كلمات مرور الراوترات بـ `AES-256-GCM` في قاعدة البيانات.
   - لا تُرسل كلمات المرور في أي طلب GET أو سجل تشغيل (Log).
3. **تدوير وإلغاء مفاتيح الوصول:**
   - إمكانية إلغاء رمز الوكيل أو مفتاح النفق بنقرة زر واحدة من لوحة الـ Super Admin في حال الاشتباه باختراق جهاز العميل.
4. **تسجيل العمليات (Audit Logging Without Secrets):**
   - توثيق أحداث: `agent:connected`, `agent:disconnected`, `router:sync_started`, `router:sync_failed`.
   - تنقية سجلات Pino لتعتيم أي كلمات مرور أو مفاتيح تشفير.
5. **التعامل مع المهلات وإعادة المحاولة:**
   - مهلة تنفيذ الأمر الواحد: 5 ثوانٍ.
   - عدد محاولات إعادة الاتصال: 3 محاولات بتباعد تصاعدي (Exponential Backoff: 1s, 3s, 7s).
6. **سلامة الحصص وعدم إيهام النجاح (Atomic Quota Consistency):**
   - عدم وسم أي دفعة كروت بأنها `COMPLETED` أو `SYNCED` إلا بعد استلام رد التأكيد الفعلي `!done` من الراوتر.
   - في حال انقطاع الاتصال أثناء المزامنة، يتم تعليم الكروت غير المكتملة بـ `FAILED` وتخفيض العداد الفعلي، لتجنب حرق حصة المشترك دون وصول الكروت لراوتره.

## 7. التوافق مع النظام الحالي والتجهيز المستقبلي لـ PPPoE

### 7.1. التأثير على مكونات النظام الحالية
- **تطبيق Flutter (Mobile):** لن يتأثر سلبياً؛ سيستمر بالاتصال بالـ API السحابي لمزامنة المبيعات وحجز الكروت دون الحاجة لمعرفة تفاصيل نفق الراوتر. وإذا تم تضمين خيار الـ Agent في تطبيق الديسكتوب، سيعمل كخدمة خلفية شفافة.
- **تطبيق الويب (React Admin):** في شاشة تفاصيل الراوتر، سيُضاف مؤشر حالة اتصال الوكيل أو النفق (VPN/Agent Status: Online / Offline) وزر "اختبار الاتصال الآمن" بدلاً من إدخال IP يدوي لا يمكن الوصول إليه.
- **خادم الـ API (NestJS):** تعديل `MikrotikClientFactory`؛ حيث يقوم بتوجيه الأوامر عبر عميل النفق أو وسيط الـ WebSocket بدلاً من محاولة عمل Direct Socket إلى IP محلي.
- **حساب الحصص والحدود:** يبقى كما هو دون أي تغيير، فالحصص مرتبطة بحسابات `Subscription` و`Tenant` في قاعدة البيانات.

### 7.2. إمكانية إضافة PPPoE مستقبلاً
- بروتوكول PPPoE في ميكروتك يعتمد على مسار أوامر مماثل للـ Hotspot تماماً:
  - Profiles: `/ppp/profile`
  - Users (Secrets): `/ppp/secret`
  - Active Connections: `/ppp/active`
- البنية المقترحة (سواءً عبر الوكيل أو نفق الـ VPN) تنقل الأوامر البرمجية الكاملة للراوتر. هذا يعني أنه بمجرد استقرار قناة الاتصال الآمنة، يمكن إضافة إدارة مشتركي الـ PPPoE مستقبلاً بمجرد إنشاء خدمة `PppoeService` مماثلة لـ `HotspotService` **دون الحاجة لإعادة كتابة أو تعديل طبقة الاتصال والشبكة نهائياً**.

### Backend (`apps/api`):
1. `apps/api/src/core/mikrotik/mikrotik-client.factory.ts`: دعم التوجيه عبر الوكيل/النفق.
2. `apps/api/src/core/mikrotik/interfaces/mikrotik-client.interface.ts`: إضافة حالات النفق ومراقبة الاتصال الحي.
3. `apps/api/src/modules/devices/devices.service.ts`: تحديث دوال فحص الاتصال ومراقبة حالة الوكلاء/الأنفاق.
4. `apps/api/src/modules/devices/dto/create-device.dto.ts`: إضافة خيار نوع الاتصال (`TUNNEL_WIREGUARD`, `TUNNEL_SSTP`, `LAN_AGENT`).
5. إنشاء وحدة جديدة: `apps/api/src/modules/agent/` أو `apps/api/src/core/tunnel/` لإدارة قنوات الوكلاء والأنفاق.

### Frontend (`apps/admin`):
1. `apps/admin/src/modules/devices/DevicesView.tsx`: تحديث نافذة إضافة الراوتر لتعرض خيارات الاتصال الآمن ورمز ربط الوكيل وسكريبت ميكروتك المولد آلياً.

### Database (`apps/api/prisma/schema.prisma`):
- إضافة حقول مساعدة لنموذج `MikroTikDevice` (مثل: `connectionMode`, `agentId`, `tunnelIp`, `lastPingAt`) بعد دراستها واعتمادها دون تدمير البيانات الحالية.

## 10. خطة اختبار واقعية (Testing & Validation Plan)

يجب الفصل التام بين الاختبارات الآلية المعزولة (Mocks) والاختبارات الميدانية الحقيقية:

### 10.1. اختبارات البيئة المعملية والميدانية (Real Hardware Tests)
1. **راوتر RouterOS 7 حقيقي:**
   - جهاز MikroTik (مثل hAP ac2 أو RB750Gr3) بنظام ROS v7.14+.
   - ربطه بشبكة Starlink أو مودم 4G يخضع لـ CGNAT (عنوان WAN يبدأ بـ `100.64.x.x`).
   - التحقق من نجاح الربط وجلب الموارد واستجابة الـ Ping في أقل من 500ms.
2. **راوتر RouterOS 6 حقيقي:**
   - جهاز MikroTik (مثل hAP lite أو RB951) بنظام ROS v6.48+.
   - التحقق من الاتصال وفعالية الأوامر.
3. **محاكاة انقطاع وعودة الإنترنت (Chaos Testing):**
   - فصل كابل الإنترنت عن الراوتر لمدة 3 دقائق أثناء محاولة إرسال دفعة كروت.
   - التحقق من تعليق المهمة بحالة `PENDING_OFFLINE`، وإعادة المزامنة التلقائية فور عودة الإنترنت دون إنشاء كروت مكررة في ميكروتك.
4. **اختبار العزل الأمني ومحاولة الاختراق (Cross-Tenant Penetration):**
   - محاولة مستأجر استدعاء راوتر مستأجر آخر عبر تعديل معرف الـ Device ID في الطلبات.
   - التحقق من اعتراض الطلب في `TenantGuard` وإرجاع `403 Forbidden` أو `404 Not Found`.

## 11. النقاط التي تتطلب معلومات أو قرارات من صاحب المشروع

قبل البدء في كتابة كود المرحلة الثالثة، نحتاج إلى توضيح القرارات التالية من العميل:

1. **طبيعة الأجهزة الفعلية لدى العملاء:**
   - هل معظم العملاء يملكون أجهزة تدعم RouterOS v7، أم أن أجهزة RouterOS v6 القديمة (مثل hAP lite) منتشرة بكثرة؟
2. **طبيعة تشغيل بيئة العميل:**
   - هل يمتلك صاحب الشبكة كمبيوتر كاشير يعمل بنظام Windows متصل بالشبكة بشكل دائم أثناء فترات البيع؟
   - إذا كان الجواب نعم: فإن خيار **LAN Agent** هو الخيار الأسرع، والأرخص ($0 تكلفة بنية إضافية)، والأسهل في الصيانة وتخطي Starlink/CGNAT، ويعمل مع Render فوراً.
3. **الميزانية المتاحة للبنية التحتية:**
   - إذا رغب العميل في اتصال مستقل 24/7 يعمل مباشرة من الراوتر حتى لو أُغلق كمبيوتر الكاشير، فهل توجد موافقة على استئجار خادم Linux VPS صغير (تكلفته حوالي $4 إلى $6 شهرياً على Hetzner) ليكون بمثابة الـ VPN Gateway المركزي للأنفاق؟
