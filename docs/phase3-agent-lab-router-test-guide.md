## 1. المقدمة والضوابط الصارمة (Strict Scope Boundaries)

> [!CAUTION]
> **ضوابط تشغيلية صارمة وغير قابلة للتجاوز:**
> 1. **ممنوع الاتصال بأي راوتر عميل حي أو تشغيلي:** يقتصر هذا الدليل حصراً على راوتر مخصص للمعمل (Lab Router / Sandbox) معزول فيزيائياً عن شبكة الإنتاج وبموافقة صريحة من مالكه.
> 2. **ممنوع النشر على Render أو تعديل إعداداته في هذه الخطوة.**
> 3. **ممنوع تطبيق أي Migration على قاعدة بيانات الإنتاج (Supabase) أو الاتصال بها.**
> 4. **ممنوع استخدام أي خدمات مدفوعة أو إنشاء تكاليف إضافية.**
> 5. **ممنوع البدء في تطوير PPPoE أو إضافة ميزات جديدة خارج نطاق HotSpot والتحقق المعملي.**
> 6. **الالتزام بالأمانة التقنية:** لا يُعلن نجاح الاختبار الميداني الحقيقي نهائياً قبل إجراء الاختبارات الفعلية على الراوتر وتوثيق المخرجات الحية منه في السجل المخصص بنهاية هذا التقرير.

## 2. جدول التمييز الصريح: المختبر فعلياً مقابل ما ينتظر الاختبار على العتاد

يوضح الجدول التالي الحدود الفاصلة بدقة بين ما جرى إثباته برمجياً وتكاملياً، وما لا يزال بانتظار التحقق الفيزيائي:

| المكوّن / العملية | حالة الاختبار الفعلي (Executed) | حالة المحاكاة (Simulation / Mock) | ما ينتظر التحقق على العتاد الحقيقي (Lab Pending) |
| :--- | :---: | :---: | :--- |
| **دورة الإقران (Pairing)** | **مختبر 100%** ضد خادم حي وتشفير DPAPI حقيقي | — | تحقق مطابقة معرّف الجهاز المسجل مع هوية الراوتر الفيزيائي. |
| **النبضات وتبادل الأوامر** | **مختبر 100%** عبر HTTP مع قاعدة PostgreSQL حية | — | استقرار النبضات أثناء حمل الشبكة المحلية الفعلي. |
| **بروتوكول Socket الثنائي** | — | **مختبر عبر MockRouter** ومفردات اختبارات الوحدة | المصافحة الثنائية (Binary Length-prefix) المباشرة مع نواة RouterOS عبر TCP port 8728/8729. |
| **تسجيل الدخول (API Login)** | — | تم التحقق من خوارزمية التشفير MD5 و Plain | التوافق الفعلي مع إصدارات RouterOS v6 القديمة والحديثة و v7. |
| **قراءة Uptime والمقاييس** | **مختبر 100%** في التكامل التام | محاكاة حقول `/system/resource/print` | استقبال الحقول وتفسيرها ومطابقتها حرفياً مع WinBox. |
| **إضافة بطاقتي Hotspot** | **مختبر 100%** في التكامل التام | محاكاة اعتراض أخطاء `!trap` | ظهور البطاقتين فعلياً في تبويب `IP -> Hotspot -> Users` في الراوتر. |
| **منع التكرار (Idempotency)** | **مختبر 100%** واسترجاع `alreadyExistingCount` | محاكاة رسائل الخطأ النصية | تطابق نص رسالة خطأ الراوتر الحقيقي مع الفحص البرمجي. |
| **حماية المستخدمين الحاليين** | **مختبر 100%** ورفض الكتابة فوق بيانات متعارضة | محاكاة الفحص | منع الوكيل من تعديل أي بطاقة عميل موجودة مسبقاً على الراوتر. |

## 3. إعدادات راوتر الاختبار المعملي (MikroTik Lab Setup)

قبل توصيل الوكيل بالراوتر المعملي، يجب تطبيق الخطوات الأمنية والإعدادية التالية بدقة من خلال موجه أوامر RouterOS (Terminal) أو تطبيق WinBox:

### 3.1 الخطوة 1: أخذ نسخة احتياطية كاملة (Mandatory Backup)
يجب تصدير وضبط نسخة احتياطية للراوتر المعملي قبل أي إجراء:
```routeros
# أخذ نسخة تصدير نصية كاملة
/export file=pre-sudafi-lab-test.rsc

# أخذ نسخة نظام احتياطية مشفرة
/system backup save name=pre-sudafi-lab-test
```
*تحقق من ظهور الملفين في قائمة `Files` في الراوتر.*

### 3.2 الخطوة 2: إنشاء مجموعة صلاحيات مقيدة (Restricted Group)
وفق مبدأ الامتيازات الأدنى (Least Privilege)، يُمنع استخدام حساب `admin` الكامل. يتم إنشاء مجموعة صلاحيات مخصصة تمنح فقط الصلاحيات اللازمة لعمل الوكيل:
```routeros
/user group add name=sudafi-agent policy=api,read,write,test comment="SudaFi LAN Agent restricted group"
```
> [!NOTE]
> **الصلاحيات المستبعدة أمنياً:** تم استبعاد الصلاحيات الخطرة مثل: `reboot` (إعادة التشغيل)، `write-sensitive` (قراءة الأسرار العميقة)، `sniff` (التنصت)، `policy` (تعديل صلاحيات المستخدمين)، و `password` (تغيير كلمات مرور المستخدمين الآخرين).

### 3.3 الخطوة 3: إنشاء مستخدم مخصص للوكيل (Dedicated User)
إنشاء مستخدم مخصص يتبع المجموعة المقيدة بكلمة مرور قوية خاصة بالمعمل:
```routeros
/user add name=sudafi-worker group=sudafi-agent password="LAB_STRONG_PASSWORD_HERE" comment="SudaFi Lab Test Worker"
```

### 3.4 الخطوة 4: تفعيل خدمة API
تفعيل منفذ API المخصص (الافتراضي 8728 غير مشفر، أو 8729 مع TLS):
```routeros
# تفعيل خدمة API القياسية للمعمل
/ip service enable api

# التحقق من أن المنفذ 8728 في حالة تشغيل
/ip service print where name="api"
```
*في حال استخدام TLS المشفر (منفذ 8729)، تأكد من تفعيل خدمة `api-ssl` وربطها بالشهادة المناسبة.*

### 3.5 الخطوة 5: التحقق من وجود سيرفر Hotspot افتراضي
يجب أن يحتوي الراوتر المعملي على خادم Hotspot نشط وبروفايل افتراضي:
```routeros
/ip hotspot print
/ip hotspot user profile print
```
*إذا كان الراوتر فارغاً، يكفي إنشاء بروفايل باسم `default` عبر: `/ip hotspot user profile add name=default`.*

## 4. فحص توافق RouterOS v6 و RouterOS v7

يحتوي محرك الاتصال [`RouterOsWorker`](file:///e:/microTik_project/apps/agent/src/router/routeros-worker.ts) على كود مدمج للتعامل مع الفروقات بين الإصدارين، ولكن يجب الانتباه للنقاط التشغيلية التالية:

| الخاصية / السلوك | RouterOS v6 | RouterOS v7 | ما يحتاج إلى فحص وتأكيد عملي على العتاد |
| :--- | :--- | :--- | :--- |
| **مصادقة تسجيل الدخول (Login)** | - v6.0-v6.42: تحدي MD5 Challenge.<br>- v6.43+: تسجيل دخول صريح (Plain). | تسجيل دخول صريح فقط (Plain Login عبر Socket). | التحقق من نجاح مصادقة `performLogin()` وتخطي مرحلة التحدي بسلاسة دون تعليق المقبس. |
| **صيغة حقول الموارد (`/system/resource/print`)** | `cpu-load`, `uptime`, `version`, `board-name` بصيغة نصية قياسية. | قد يتضمن `version` إضافات نصية مثل `7.14.3 (stable)` أو تفاصيل النواة. | التأكد من أن دالة تحليل الأرقام `parseInt` لا تستقبل `NaN` وتستخرج نسبة المعالج والذاكرة بدقة. |
| **نص رسالة الخطأ عند التكرار (`!trap`)** | `failure: already have user with this name` | `failure: already have user with this name` | التأكد من أن الشرط `msg.includes('already have user with this name')` يلتقط الرسالة حرفياً في كلا الإصدارين. |
| **تحديد الوقت وحجم البيانات** | يقبل `limit-uptime=1h` أو صيغة الثواني، و `limit-bytes-total`. | يدعم نفس المحددات، ولكن تتطلب v7 أحياناً قيماً رقمية مجردة في واجهات معينة. | التأكد من قبول الراوتر للقيم المرسلة في حقول `limitUptime` و `limitBytesTotal`. |

## 5. دليل الاختبار العملي خطوة بخطوة (Step-by-Step Execution Guide)

تم تزويد وكيل الويندوز بأداة فحص واختبار مخبرية مدمجة [`test-hotspot`](file:///e:/microTik_project/apps/agent/src/main.ts) لاختبار العتاد المعملي بشكل مستقل وآمن قبل ربطه بالسيرفر.

### الخطوة 1: ضبط ملف إعدادات الوكيل للاتصال بالراوتر المعملي
في مجلد الوكيل `apps/agent/`، انسخ الملف النموذجي إلى `agent.config.json` وضع بيانات الراوتر المعملي:
```json
{
  "serverUrl": "http://127.0.0.1:3000/api/v1",
  "agentName": "Lab-Tester-PC",
  "heartbeatIntervalMs": 25000,
  "httpTimeoutMs": 60000,
  "maxRetries": 5,
  "mockRouter": false,
  "router": {
    "host": "192.168.88.1",
    "port": 8728,
    "username": "sudafi-worker",
    "password": "LAB_STRONG_PASSWORD_HERE",
    "useSsl": false,
    "timeoutMs": 10000,
    "rosVersion": "v7"
  }
}
```
*(احرص على ضبط `"mockRouter": false` لتفعيل الاتصال الفيزيائي الحقيقي).*

---

### الخطوة 2: اختبار الاتصال وقراءة الـ Uptime وحالة الراوتر
شغّل أمر الفحص الأولي للاتصال:
```powershell
pnpm --filter @mikrotik-saas/agent start -- test-router
```
**النتيجة المتوقعة على الشاشة:**
```text

========================================================
Testing connection to MikroTik router at 192.168.88.1:8728...

Version:      7.14.3 (stable)

CPU Load:     3%
Free Memory:  214 MB
```

**التحقق الميداني المطلوب من المختبر:**
- افتح تطبيق WinBox، واذهب إلى `System -> Resources`.
- طابق قيمة `Uptime` ونسبة `CPU Load` ومقدار `Free Memory` مع ما طُبع في الطرفية.

### الخطوة 3: اختبار إضافة بطاقتي Hotspot، وفحص منع التكرار وحماية المستخدمين
تم دمج هذا السيناريو الكامل في أمر واحد منظم ينفذ الخطوات الخمس بتسلسل ذري آمن:

```powershell
# لتنفيذ الاختبار مع الإبقاء على البطاقتين مؤقتاً لمعاينتهما في WinBox:
pnpm --filter @mikrotik-saas/agent start -- test-hotspot --keep

# أو لتنفيذ الاختبار مع الحذف التلقائي وإعادة الراوتر لحالته الأصلية فوراً:
pnpm --filter @mikrotik-saas/agent start -- test-hotspot
```

#### تفاصيل التسلسل البرمجي المنفذ خلال الاختبار:
1. **المرحلة 1 — إضافة بطاقتي الاختبار:**
   - يرسل الوكيل طلب إضافة مستخدمين تجريبيين:
     * البطاقة 1: `name: "sudafi_lab_01"`, `password: "lab_pass_01"`, `profile: "default"`, `comment: "sudafi-lab-test"`.
     * البطاقة 2: `name: "sudafi_lab_02"`, `password: "lab_pass_02"`, `profile: "default"`, `comment: "sudafi-lab-test"`.
   - **التحقق:** طباعة `Created: 2, Existing: 0, Failed: 0`.
2. **المرحلة 2 — التحقق من وجود المستخدمين في الراوتر:**
   - يرسل الوكيل أمر `/ip/hotspot/user/print =.proplist=name` للتأكد من وجودهما في جدول الراوتر.
   - **التحقق:** طباعة `Found: [sudafi_lab_01, sudafi_lab_02], Missing: []`.
3. **المرحلة 3 — اختبار منع التكرار (Idempotency):**
   - يعيد الوكيل إرسال نفس البطاقتين مرة أخرى لمحاكاة فقدان الإشعار (Lost ACK).
   - يعترض الوكيل خطأ التكرار من الراوتر، ويفحص مواصفات المستخدم القائم، ويتعرف عليهما دون خطأ.
   - **التحقق:** طباعة `Re-run: Created: 0, AlreadyExisting: 2, Failed: 0` ورسالة `IDEMPOTENCY TEST PASSED`.
4. **المرحلة 4 — اختبار حماية المستخدمين الحاليين من التعارض (Conflict Protection):**
   - يرسل الوكيل محاولة إضافة مستخدم يحمل نفس الاسم `sudafi_lab_01` ولكن ببروفايل مختلف كلياً (`profile: "different_profile"`).
   - يكتشف الوكيل أن البروفايل غير متطابق، فيرفض العملية فوراً لحماية البطاقة الأصلية من التلف أو التعديل غير المصرح به.
   - **التحقق:** طباعة `Conflict probe outcome: Failed: 1, Created: 0` ورسالة `CONFLICT PROTECTION PASSED`.
5. **المرحلة 5 — التنظيف واستعادة الحالة الصفرية (Rollback / Cleanup):**
   - إذا لم يُمرر الخيار `--keep`، يقوم الوكيل بحذف البطاقتين تجريبياً عبر `/ip/hotspot/user/remove`.
   - **التحقق:** طباعة `Removed: 2, Not Found: 0, Failed: 0` ورسالة `CLEANUP COMPLETED: Router restored to original state`.

## 6. إدارة تشغيل وإيقاف Windows Agent

### 6.1 التشغيل التفاعلي المباشر (Interactive Run)
يوصى بالتشغيل التفاعلي أثناء جلسات الاختبار المعملية لمراقبة السجلات الحية فورياً:
```powershell
# بدء تشغيل الوكيل
pnpm --filter @mikrotik-saas/agent start -- run

# لإيقاف الوكيل:
# اضغط على لوحة المفاتيح: Ctrl + C
```
*عند الضغط على `Ctrl + C`، يستمع الوكيل لإشارة `SIGINT` ويقوم بإيقاف مؤقت النبضات وإغلاق مقبس الاتصال مع الراوتر بنظافة.*

### 6.2 فحص حالة الإقران ومسار التخزين
```powershell
pnpm --filter @mikrotik-saas/agent start -- status
```
*يعرض هذا الأمر معرّف الوكيل، والراوتر المقترن به، ومسار ملف الاعتماد المشفر بواسطة DPAPI.*

### 6.3 إدارة المهمة المجدولة (Scheduled Task Management)
في حال تجربة التشغيل في الخلفية على نظام ويندوز:
```cmd
:: تثبيت المهمة المجدولة (يتطلب تشغيل كمسؤول)
apps\agent\scripts\install-windows-service.bat

:: التحقق من وجود المهمة وحالتها في Windows
schtasks /query /tn "SudaFiAgent" /fo LIST /v

:: تشغيل المهمة فوراً
schtasks /run /tn "SudaFiAgent"

:: إيقاف المهمة
schtasks /end /tn "SudaFiAgent"

:: إزالة المهمة بالكامل
apps\agent\scripts\uninstall-windows-service.bat
```

## 7. إجراءات الاستعادة وتطهير الراوتر (Rollback & Clean-up Runbook)

في نهاية أي جلسة اختبار معملية، يجب التأكد من خلو الراوتر من أي بيانات اختبارية أو بقايا غير مرغوب فيها:

### 7.1 الحذف اليدوي لبطاقات الاختبار عبر Terminal في الراوتر
إذا استخدمت الخيار `--keep` لمعاينة البطاقات في WinBox، يمكنك مسحها يوماً عبر الأمر:
```routeros
/ip hotspot user remove [find comment="sudafi-lab-test"]
```

### 7.2 إزالة مستخدم ومجموعة الاختبار
```routeros
/user remove [find name="sudafi-worker"]
/user group remove [find name="sudafi-agent"]
```

### 7.3 استعادة ملف التهيئة الأصلي (Full Rollback)
في حال حدوث أي خطأ غير متوقع أثناء ضبط الراوتر، استعد النسخة الأصلية المحفوظة في الخطوة 3.1:
```routeros
/import file-name=pre-sudafi-lab-test.rsc
```

### 7.4 تطهير بيانات اعتماد الوكيل محلياً (Unpair)
لتصفير الوكيل محلياً وإلغاء إقرانه من جهاز الكمبيوتر:
```powershell
pnpm --filter @mikrotik-saas/agent start -- unpair
```
*يقوم هذا الأمر بمسح ملف `credentials.enc` المشفر بواسطة DPAPI وتصفير ذاكرة الوكيل.*

## 9. الخلاصة والتوصية التشغيلية
