# خطة التنفيذ الفنية لوكيل الشبكة المحلية (SudaFi LAN Agent)
**وثيقة التخطيط الهندسي الشاملة للمرحلة الثالثة: الاتصال الآمن بأجهزة MikroTik خلف Starlink وCGNAT**  
**المسار:** `E:\microTik_project`  
**تاريخ التحديث:** 10 أكتوبر 2026  
**الإصدار:** 2.0 (خطة معمارية منقحة ومدققة أمنياً)  
**الحالة:** بانتظار الاعتماد النهائي قبل كتابة الكود (Pending User Approval)

## 1. اختيار التقنية ونطاق دعم الأجهزة (Technology & Hardware Scope)

### 1.1. مقارنة التقنيات المتاحة للوكيل
لتشغيل وكيل خفيف وموثوق داخل شبكة العميل، تمت مقارنة الخيارات البرمجية الرئيسية لأنظمة التشغيل:

| التقنية | حجم الملف المترجم | استهلاك الذاكرة (RAM) | التبعيات المطلوبة | تشغيل كخدمة Windows Service | التقييم الهندسي والقرار |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Go (Golang v1.22+)** | ~12 - 16 MB | **15 - 25 MB** | **صفر (Zero Dependencies)** | **أصلي ومباشر** عبر حزمة `golang.org/x/sys/windows/svc` | **الخيار الأساسي المعتمد للمرحلة الحالية.** |
| **Node.js (عبر pkg/nexe)** | ~45 - 60 MB | **50 - 80 MB** | محرك V8 المترجم داخلياً | يحتاج أدوات خارجية مثل `winsw` | ثقيل نسبياً واستهلاك الذاكرة أعلى بـ 3 أضعاف. |
| **.NET C# (Native AOT)** | ~25 - 35 MB | **30 - 45 MB** | يتطلب بيئة تشغيل حديثة | مدمج عبر `WindowsServiceLifetime` | جيد، لكن حجم الحزمة أعلى وتوافقه مع ويندوز القديم أقل. |

### 1.2. النطاق الإلزامي للمرحلة الحالية مقابل الدعم المستقبلي
- **نطاق المرحلة الثالثة الإلزامي (Phase 3 Scope):**
  - بناء تطبيق ويندوز مستقل `sudafi-agent.exe` كملف تنفيذي مجمع بالكامل دون أي رنتايم خارجي.
  - يدعم وضعين للتشغيل:
    1. **التشغيل المباشر كبرنامج سطح مكتب/موجه أوامر:** بالضغط المزدوج أثناء فترات العمل اليومية.
    2. **التشغيل كخدمة نظام أصلية (`Windows Service`):** يبدأ تلقائياً مع إقلاع الجهاز ويعمل في الخلفية بصمت (`sudafi-agent.exe install`).
  - متوافق مع: Windows 10, Windows 11, Windows Server 2016+, وWindows 7/8.1 (64-bit & 32-bit).
- **الدعم المستقبلي (مستبعد من المرحلة الحالية - Out of Scope):**
  - دعم أنظمة Linux ARM (أجهزة Orange Pi وRaspberry Pi وTV Boxes) يُفصل كمسار مستقبلي منفصل لتجنب تشتيت متطلبات الصيانة وبناء صور النظام.

### 1.3. متطلبات جهاز العميل وحقيقة الحاجة للتشغيل الدائم
- **الحد الأدنى لمواصفات الكمبيوتر:** معالج عادي 1.0 GHz، ذاكرة 512 MB (استهلاك الوكيل < 25 MB)، مساحة قرص 30 MB، وبطاقة شبكة متصلة بنطاق LAN الراوتر (`192.168.88.x`).
- **هل يحتاج العميل لكمبيوتر دائم التشغيل (24/7)؟**
  - **لتوليد وطباعة دفعات الكروت:** **لا نهائياً.** يتم تشغيل الكمبيوتر لمزامنة الدفعة (مثلاً 500 كرت) التي تُكتب فوراً داخل ذاكرة الراوتر. بعد انتهاء المزامنة والطباعة، يمكن إغلاق الكمبيوتر بالكامل وتستمر شبكة الهوتسبوت في العمل ويستمر المشتركون في الاتصال دون أدنى تأثر.
  - **للعمليات الإدارية اللحظية (Real-Time Control):** مثل قطع اتصال مستخدم نشط حالياً أو فحص استهلاك البيانات المباشر، يشترط أن يكون جهاز الوكيل قيد التشغيل ومتصلاً بالإنترنت لحظة تنفيذ الطلب.
- **حدود وضع الربط الميداني عبر Flutter (Mobile Direct LAN Limitations):**
  - تطبيق Flutter يمكنه التخاطب مع راوتر MikroTik عبر المنفذ 8728 **فقط** عندما يكون الهاتف متصلاً بنفس شبكة الـ Wi-Fi المحلية للراوتر.
  - **لا يمكن** لتطبيق الهاتف أن يحل محل الوكيل الدائم أو أن يعمل كخدمة خلفية 24/7؛ لأن أنظمة Android وiOS الحديثة تقتل العمليات الخلفية فور إغلاق الشاشة أو توفير الطاقة.
  - هو حل ميداني طارئ للمزامنة اليدوية أثناء تواجد المشرف في الموقع، وليس بديلاً لـ SudaFi LAN Agent.

## 2. أمان دورة الإقران والصلاحيات (Pairing Security & RBAC)

```
[ المشرف / لوحة الإدارة ]            [ NestJS API Gateway ]            [ SudaFi LAN Agent ]
          │                                     │                                 │
          │ 1. طلب رمز إقران للراوتر            │                                 │
          ├────────────────────────────────────>│                                 │
          │ 2. إنشاء رمز مؤقت (صالح لـ 5 دقائق) │                                 │
          │    (مخزن كـ Hash في قاعدة البيانات) │                                 │
          │<────────────────────────────────────┤                                 │
          │                                     │                                 │
          │ 3. العميل يدخل الرمز في الوكيل      │                                 │
          │                                     │ 4. طلب الإقران (رمز + مواصفات)  │
          │                                     │<────────────────────────────────┤
          │                                     │ 5. فحص المحاولات والتحقق الذري  │
          │                                     │    وإصدار AgentAuthToken        │
          │                                     ├────────────────────────────────>│
          │                                     │    (تشفير محلي عبر DPAPI)       │
          │ 6. تحديث حالة الراوتر: وكيل مقترن   │                                 │
          │<────────────────────────────────────┤                                 │
```

### 2.1. حماية رمز الإقران ذي الستة أرقام (Pairing Code Hardening)
- **فترة الصلاحية:** صلاحية صارمة لمدة **5 دقائق** فقط (بعدها يُلغى تلقائياً).
- **الاستخدام لمرة واحدة (Single-Use Atomic Consumption):** بمجرد قبول الرمز، يُحذف فوراً في معاملة ذرية تمنع أي محاولة إعادة استخدام (Anti-Replay).
- **الحماية من التخمين الآلي (Rate Limiting & Lockout):**
  - يُسمح بحد أقصى **3 محاولات خاطئة** لكل عنوان IP ولكل راوتر.
  - بعد 3 محاولات فاشلة، يُقفل الراوتر وعنوان الـ IP عن محاولات الإقران لمدة **15 دقيقة** برمز `HTTP 429 Too Many Requests`.
- **التخزين المشفر للرمز:** لا يُخزن الرمز كنص صريح، بل يُخزن كـ `HMAC-SHA256(secret, code + salt)` في جدول `agent_pairing_codes`.

### 2.2. التحقق الثلاثي الصارم من الملكية عند تنفيذ كل أمر (Triple-Check RBAC)
**لا يثق الخادم أبداً في الـ `tenantId` الموجود داخل الـ Token وحده.** عند تنفيذ أي أمر عبر بوابة الوكيل:
1. **فحص صلاحية المستخدم الطالب:** التحقق من امتلاك المستخدم لـ `Permission` المطلوبة (مثل `cards:create` أو `devices:manage`) لنفس الـ `tenantId`.
2. **فحص ملكية الراوتر:** الاستعلام من جدول `mikrotik_devices` للتأكد من أن `deviceId` المستهدف ينتمي بالفعل وبشكل حصري لنفس الـ `tenantId`.
3. **فحص اقتران الوكيل النشط:** التأكد من أن مقبس الـ WebSocket المتصل حالياً مقترن صراحة بهذا الـ `deviceId` والـ `tenantId`، وأن حالة الوكيل في جدول `device_agents` هي `ONLINE` وغير ملغاة (`status != REVOKED`).
- إذا فشل أي فحص من الفحوصات الثلاثة، يُلغى الطلب فوراً برمز `403 Forbidden` ويُسجل في جدول `audit_logs`.

### 2.3. الإلغاء الفوري للصلاحيات (Instant Revocation)
- عند ضغط زر "إلغاء ربط الوكيل (Revoke Agent)" في لوحة الإدارة:
  1. يُحدث سجل الوكيل في قاعدة البيانات إلى `status: REVOKED` مع تسجيل `revokedAt`.
  2. يُغلق مقبس الـ WebSocket الخاص بالوكيل فوراً من الذاكرة برمز `4403 Forbidden`.
  3. يتم إدراج `tokenHash` في قائمة سوداء في الذاكرة لمنع إعادة الاتصال حتى لو احتفظ الوكيل بالتوكن.

## 3. إدارة الأسرار وحماية بيانات الاعتماد (Secrets Management)

### 3.1. مصدر وتخزين ونقل كلمات مرور MikroTik
1. **المصدر والتخزين المركزي:**
   - يُدخل العميل كلمة مرور الراوتر واسم المستخدم عند إضافة الراوتر من لوحة الإدارة.
   - تُخزن كلمة المرور مشفرة في قاعدة بيانات PostgreSQL داخل جدول `mikrotik_devices` كـ `passwordEncrypted` باستخدام تشفير **AES-256-GCM** مع `iv` و `authTag` فريدين ومفتاح التشفير السحابي `ENCRYPTION_KEY`.
2. **النقل الآمن (Ephemeral In-Memory Dispatch):**
   - تُفك شفرة كلمة المرور في خادم NestJS لحظياً فقط عند الحاجة لتنفيذ أمر على الراوتر.
   - تُرسل كلمة المرور داخل حمولة الأمر (Command Payload) المشفرة عبر نفق TLS 1.3 (WSS) الخاص بالوكيل.
3. **الاستخدام والإتلاف على جهاز الوكيل:**
   - يحتفظ الوكيل بكلمة المرور في الذاكرة الحية (RAM) فقط أثناء فتح اتصال الـ Socket المحلي مع الراوتر (`192.168.88.1:8728`).
   - فور انتهاء الأمر أو انقطاع الاتصال، يتم تصفير متغيرات كلمة المرور من الذاكرة (`zeroize RAM buffer`).
   - **لا تُحفظ كلمة مرور الراوتر على قرص جهاز العميل نهائياً.**

### 3.2. تشفير توكن الوكيل محلياً (AgentAuthToken Storage)
- **على أنظمة Windows:**
  - يتم تشفير الرمز باستخدام **Windows Data Protection API (DPAPI)** عبر استدعاء `CryptProtectData` بنطاق الجهاز (`CRYPTPROTECT_LOCAL_MACHINE`).
  - يُحفظ الناتج المشفر في ملف محمي الصلاحيات: `%ProgramData%\SudaFi\agent.dat`.
  - هذا يضمن أنه حتى لو تم نسخ الملف إلى جهاز آخر، لن يتمكن أي طرف من فك تشفيره.
- **الأنظمة المستقبلية (Linux):**
  - حفظ الملف بصلاحيات صارمة `0600` تحت مستخدم نظام غير متميز `sudafi-agent`، أو دمجها مع `systemd-creds` وLinux Keyring.

### 3.3. سياسة السجلات النظيفة (Strict Zero-Credential Logging)
- يُحظر كلياً طباعة أي حقول حساسة (`password`, `token`, `code`, `authTag`, `passwordEncrypted`) في سجلات NestJS أو الوكيل.
- تطبيق طبقة تنقية (Sanitization Interceptor) تعترض جميع الرسائل قبل كتابتها في السجلات وتستبدل أي حقل حساس بـ `[REDACTED]`.

## 4. سلامة إنشاء الكروت ومنع التكرار (Card Generation & Idempotency)

```
[ NestJS Cards Service ]                 [ SudaFi LAN Agent ]               [ MikroTik RouterOS ]
          │                                       │                                  │
          │ 1. أمر إضافة دفعة (operationId)       │                                  │
          ├──────────────────────────────────────>│                                  │
          │                                       │ 2. إنشاء المستخدمين محلياً       │
          │                                       ├─────────────────────────────────>│
          │                                       │    (/ip/hotspot/user/add)        │
          │                                       │<─────────────────────────────────┤
          │                                       │                                  │
          │      ⚡ انقطاع الاتصال قبل التأكيد ⚡ │                                  │
          │                                       │                                  │
          │ 3. إعادة إرسال الأمر (نفس operationId)│                                  │
          ├──────────────────────────────────────>│                                  │
          │                                       │ 4. فحص استعلامي ومطابقة دقيقة    │
          │                                       │    (/ip/hotspot/user/print)      │
          │                                       ├─────────────────────────────────>│
          │                                       │    فحص: comment == batchNumber   │
          │                                       │         profile == targetProfile │
          │                                       │<─────────────────────────────────┤
          │                                       │                                  │
          │ 5. تقرير مفصل لكل كرت (مكتمل / تضارب) │                                  │
          │<──────────────────────────────────────┤                                  │
```

### 4.1. خطورة افتراض نجاح الكروت الموجودة مسبقاً
- **المشكلة:** إذا رد الراوتر بـ `failure: already have user with this name`، قد يكون هذا الاسم لمستخدم قديم، أو منتهي الصلاحية، أو حساب خاص. اعتباره نجاحاً عشوائياً سيؤدي إلى:
  1. الإبلاغ عن نجاح كاذب لكرت لا يتبع هذه الدفعة.
  2. تسليم كود غير صالح للمشترك النهائي.
  3. استهلاك غير مبرر لحصة المستأجر الشهرية.

### 4.2. آلية المطابقة والتحقق الصارمة (Reconciliation Protocol)
عند إعادة إرسال أمر إضافة كروت بنفس الـ `operationId`، أو عند مواجهة كرت موجود مسبقاً:
1. **يقوم الوكيل بتعليق القرار وإجراء استعلام فوري:**
   `/ip/hotspot/user/print where name=username`
2. **فحص الحقول ومطابقتها:**
   - هل حقل الملاحظة `comment` يطابق `batchNumber` الحالي؟
   - هل حقل البروفايل `profile` يطابق البروفايل المطلوب للدفعة؟
   - هل حدود الوقت والبيانات متطابقة؟
3. **اتخاذ القرار الحتمي:**
   - **إذا تطابقت الحقول:** يُعتبر الكرت قد أُنشئ فعلاً في المحاولة السابقة المنقطعة، ويُوسم بـ `SYNCED`.
   - **إذا لم تتطابق الحقول:** يُسجل الكرت كحالة تضارب خطيرة (`COLLISION_ERROR`). لا يُعتبر الكرت ناجحاً، ولا يُحسب ضمن حصة الدفعة، ويُعاد الخطأ للخادم ليقوم بتوليد كرت بديل برقم تسلسلي جديد.

### 4.3. سجل تتبع حالة كل عنصر (Per-Item State Ledger)
الوكيل يعيد تقريراً تفصيلياً يحدد مصير كل كرت:
```json
{
  "operationId": "op_9c71a-4d2b",
  "batchNumber": "B2610-A01",
  "items": [
    { "username": "78492015", "status": "SYNCED", "details": "CREATED_NEW" },
    { "username": "78492016", "status": "SYNCED", "details": "RECONCILED_MATCHED" },
    { "username": "78492017", "status": "FAILED", "reason": "COLLISION_EXISTING_USER_DIFFERENT_PROFILE" }
  ],
  "syncedCount": 2,
  "failedCount": 1
}
```
- في قاعدة بيانات المنصة، تظل الكروت الفاشلة بحالة `FAILED`، ولا تُحسب ضمن الحصة المستهلكة نهائياً.

## 5. بروتوكول الأوامر التطبيقية المغلقة (Typed RPC Protocol)

### 5.1. حظر الأوامر العامة نهائياً
يُمنع كلياً تزويد الوكيل بواجهة تمرير نصوص أو أوامر عامة عشوائية (`Raw CLI Pass-Through`)؛ لمنع استغلال الوكيل في حال حدوث أي اختراق.

### 5.2. قائمة الأوامر التطبيقية المعتمدة ومخططات التحقق (Whitelisted Schemas)
يتم التحقق من نوع ومدخلات كل أمر عبر Schema صارمة:

1. `hotspot.user.batch_add`:
   - `operationId`: UUIDv4
   - `batchNumber`: نص (أحرف وأرقام وشرطة فقط)
   - `users`: مصفوفة (بحد أقصى 500 عنصر في الدفعة)، كل عنصر يحتوي على:
     - `name`: نص بطول 4 إلى 32 حرفاً
     - `password`: نص بطول 4 إلى 32 حرفاً
     - `profile`: اسم البروفايل المطابق
     - `uptimeLimit`: اختياري (تنسيق ميكروتك مثل `1h` أو `30m`)
     - `bytesLimit`: اختياري (رقم صحيح موجب)
2. `hotspot.user.remove`:
   - `username`: اسم الكرت المطلوب حذفه.
3. `hotspot.user.verify_batch`:
   - `batchNumber`: رقم الدفعة.
   - `usernames`: قائمة الأسماء المطلوب مطابقتها.
4. `hotspot.session.list`:
   - جلب الجلسات النشطة وعناوين IP وMAC واستهلاك البيانات.
5. `system.router.health`:
   - فحص استجابة الراوتر، المعالج، الذاكرة، وإصدار RouterOS.

### 5.3. الفصل المعماري بين طبقة النقل وخدمات البروتوكولات
```
┌─────────────────────────────────────────────────────────────┐
│             طبقة النقل والاتصال (Transport Layer)            │
│   AgentWebSocketTransport (التشفير، النبضات، إعادة الاتصال)  │
└──────────────────────────────┬──────────────────────────────┘
                               │
            ┌──────────────────┴──────────────────┐
            ▼                                     ▼
┌──────────────────────────────┐    ┌──────────────────────────────┐
│  خدمة الهوتسبوت (HotSpot)    │    │    خدمة الـ PPPoE القادمة    │
│  - hotspot.user.batch_add    │    │  - pppoe.secret.add          │
│  - hotspot.user.remove       │    │  - pppoe.secret.remove       │
│  - hotspot.session.list      │    │  - pppoe.session.list        │
└──────────────────────────────┘    └──────────────────────────────┘
```
- طبقة النقل لا تعرف طبيعة الأمر؛ هي تنقل رسائل RPC الموقعة.
- إضافة ميزة **PPPoE** مستقبلاً تتطلب فقط إضافة معالج `PppoeAgentHandler` على نفس النفق دون المساس بطبقة الاتصال.

## 6. بيئة النشر على Render وتدقيق اتصالات WebSocket

### 6.1. فصل الحقائق المثبتة عن الافتراضات التي تحتاج لاختبار
لتجنب المفاجآت التشغيلية في بيئة الإنتاج:

| العنصر | حقيقة مثبتة (Verified Fact) | افتراض غير مثبت (Unverified Assumption) | المعالجة الهندسية |
| :--- | :--- | :--- | :--- |
| **دعم WebSocket** | يدعم Render بروتوكول WSS عبر المنفذ 443 وشهادة Cloudflare. | افتراض أن اتصال WebSocket المفتوح يمنع نوم خوادم Render Free للأبد. | **الحقيقة:** خوادم Render Free تنام وتوقف التشغيل. **الحل:** الإقرار بأن باقة **Render Starter ($7/شهر)** إلزامية للتشغيل التجاري المستقر للوكلاء. |
| **مهلة الاتصال الخامل** | بوابات Render وCloudflare تسقط اتصالات TCP الخاملة بعد 100 ثانية تقريباً. | افتراض أن إرسال نبضات كل 25 ثانية يكفي دون فحص طرف العميل. | اعتماد نبضات مزدوجة: الوكيل يرسل Ping كل 20 ثانية، والخادم يسقط الجلسة إن غاب الرد لأكثر من 45 ثانية. |
| **زمن استعادة الاتصال** | - | افتراض استعادة الاتصال في أقل من 2 ثانية في كل الظروف. | **الحقيقة:** شبكات Starlink و3G تعاني من تقلبات في زمن الاستجابة. **الحل:** خوارزمية إعادة محاولة متكيفة (1s $\rightarrow$ 30s) دون التعهد بزمن ثابت غير واقعي. |
| **ذاكرة الخادم** | خادم NestJS يستهلك ذاكرة إضافية لكل اتصال WebSocket مفتوح. | افتراض إمكانية استيعاب آلاف الوكلاء على باقة 512MB RAM دون تدقيق. | وضع حد أقصى للاتصالات المتزامنة لكل خادم ومراقبة مقاييس الذاكرة في الـ Backend. |

## 7. تعديلات قاعدة البيانات وخطة الترحيل (Database Schema)

تعديلات آمنة وتراكمية بنسبة 100% دون مساس بأي جداول حالية:

```prisma
enum AgentStatus {
  ONLINE
  OFFLINE
  REVOKED
}

model DeviceAgent {
  id              String      @id @default(uuid())
  tenantId        String
  deviceId        String      @unique // وكيل نشط واحد لكل راوتر
  name            String      // اسم الكمبيوتر المضيف (مثال: "Cashier-PC")
  tokenHash       String      @unique // SHA-256 Hash لرمز الوصول
  status          AgentStatus @default(OFFLINE)
  version         String?     // إصدار الوكيل
  ipAddress       String?     // عنوان IP الخارجي
  lastPingAt      DateTime?
  pairedAt        DateTime    @default(now())
  revokedAt       DateTime?
  createdAt       DateTime    @default(now())
  updatedAt       DateTime    @updatedAt

  tenant Tenant         @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  device MikroTikDevice @relation(fields: [deviceId], references: [id], onDelete: Cascade)

  @@index([tenantId])
  @@index([deviceId])
  @@index([status])
  @@map("device_agents")
}

model AgentPairingCode {
  id          String   @id @default(uuid())
  tenantId    String
  deviceId    String
  codeHash    String   @unique // HMAC-SHA256 Hash
  attempts    Int      @default(0) // عداد المحاولات الفاشلة لمنع التخمين
  expiresAt   DateTime
  createdAt   DateTime @default(now())

  @@index([codeHash])
  @@index([deviceId])
  @@map("agent_pairing_codes")
}
```

## 8. مصفوفة الاختبارات المعملية والميدانية (Testing Scenarios)

### 8.1. الاختبارات الآلية (Jest Automated Tests)
1. **اختبار التخمين (Pairing Brute-Force):** إرسال 4 محاولات خاطئة لرمز الإقران؛ التأكد من حظر الطلب الرابع برمز `429 Too Many Requests` وقفل المحاولات.
2. **اختبار الاستخدام لمرة واحدة (Single-Use Token):** استخدام رمز الإقران بنجاح، ثم محاولة استخدامه مرة أخرى؛ التأكد من رفضه برمز `400 Bad Request`.
3. **اختبار عزل المستأجرين (Tenant Boundary Enforcement):** محاولة إرسال أمر لراوتر مستأجر آخر باستخدام توكن وكيل صالح؛ التأكد من رفض الطلب برمز `403 Forbidden` وتسجيله في `AuditLog`.
4. **اختبار الإلغاء الفوري (Instant Revocation):** إلغاء الوكيل أثناء اتصاله، والتحقق من قطع اتصال WebSocket فوراً ورفض أي محاولة لاحقة.
5. **اختبار مطابقة الكروت (Card Reconciliation Test):** محاكاة انقطاع الاتصال بعد إضافة 50 كرت من أصل 100، وإعادة إرسال نفس الأمر؛ التأكد من مطابقة الكروت المنشأة واستكمال الباقي دون تكرار أو أخطاء.
6. **اختبار تضارب الأسماء (Collision Detection):** محاكاة وجود كرت قديم باسم مطابق؛ التأكد من وسمه بـ `COLLISION_ERROR` وعدم احتسابه في الحصة.

### 8.2. الاختبارات الميدانية الحقيقية (Physical Hardware Matrix)
*يتم الفصل التام بين نتائج المحاكاة والاختبارات الحقيقية:*
1. **اختبار راوتر RouterOS 7 (MikroTik RB750Gr3):**
   - متصل خلف اتصال Starlink خاضع لـ CGNAT بدون Public IP.
   - تشغيل الوكيل على جهاز Windows 10 محلي.
   - مزامنة 100 كرت، والتحقق بالعين المجردة عبر WinBox.
2. **اختبار راوتر RouterOS 6 (MikroTik hAP lite v6.48):**
   - راوتر قديم بمعالج MIPSBE ومساحة تخزين 16MB لا يدعم WireGuard.
   - التحقق من نجاح مصادقة Socket API القديمة (MD5 challenge) وإضافة الكروت بسلاسة.
3. **اختبار فصل كابل الشبكة وإعادة التشغيل:**
   - فصل كابل الإيثرنت أثناء تنفيذ الدفعة، وإعادة وصله، والتحقق من استعادة الجلسة ومطابقة الحصص تلقائياً.
