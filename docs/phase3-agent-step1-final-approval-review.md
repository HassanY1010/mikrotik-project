## 1. فحص ملف التهجير وآلية قفل سجل الراوتر (Migration & Row-Level Lock)

### أ) فحص ملف التهجير الفعلي (`migration.sql`)
الملف المعني: `apps/api/prisma/migrations/20261010230000_add_device_agent_and_pairing/migration.sql`

يتضمن الملف الإجراءات الهيكلية التالية:
1. إنشاء جدول الوكلاء `device_agents` وجداول الرموز والمحاولات `agent_pairing_codes` و `agent_pairing_attempts`.
2. إضافة المفاتيح الأجنبية مع خاصية الحذف المتتالي `ON DELETE CASCADE`.
3. إضافة القيد الفريد الجزئي (Partial Unique Index) الحاسم في السطر 60:
   ```sql
   CREATE UNIQUE INDEX "device_agents_active_device_idx" 
   ON "device_agents"("deviceId") 
   WHERE "status" != 'REVOKED';
   ```

### ب) هل القفل المستخدم هو فعلًا قفل صف PostgreSQL (Row-Level Lock)؟
في ملف `apps/api/src/modules/agent/agent.service.ts` (الأسطر 231-235)، تنفذ المعاملة ما يلي:
```typescript
await tx.mikroTikDevice.update({
  where: { id: matchedCodeRecord!.deviceId },
  data: { updatedAt: now },
});
```

**التحليل الفني المعياري لمحرك PostgreSQL:**
- **نعم، هو قفل صفي حقيقي تماماً.**
- عند تنفيذ استعلام `UPDATE "mikrotik_devices" SET "updatedAt" = $1 WHERE "id" = $2` داخل كتلة معاملة (`BEGIN ... COMMIT`)، يقوم محرك PostgreSQL فورياً بحجز قفل من نوع `RowExclusiveLock` على مستوى الجدول، وقفل حصري على مستوى السجل نفسه (Tuple Lock عبر حقل `XMAX` في رأس السطر المقفل).
- هذا يعادل تماماً من الناحية العملية والأمنية استعلام `SELECT ... FOR UPDATE`؛ إذ يمنع أي معاملة متزامنة أخرى من قراءة السجل بغرض التحديث أو تعديله، ويجبر أي معاملة ثانية تحاول تحديث الراوتر نفسه على الانتظار في طابور محرك PostgreSQL حتى تصدر المعاملة الأولى `COMMIT` أو `ROLLBACK`.

### ج) هل يمنع طلبين متزامنين من إنشاء وكيلين نشطين لنفس الراوتر؟
**نعم، ويتحقق ذلك عبر خطين دفاعيين متكاملين (Two-Tier Guarantee):**

1. **الخط الدفاعي الأول: التسلسل المعاملي داخل محرك قاعدة البيانات (Serialization via Row Lock)**
   - **السيناريو 1 (طلبين بنفس رمز الإقران):** أول طلب ينفذ `updateMany` على `agent_pairing_codes` يضبط `isConsumed = true`. الطلب الثاني يجد `count === 0` ويلقي `ConflictException` فوراً ويتوقف دون المساس بالراوتر أو الوكيل.
   - **السيناريو 2 (طلبين متزامنين برمزين مختلفين للراوتر نفسه):**
     - الطلب (أ) يستهلك رمزه، ثم ينفذ `tx.mikroTikDevice.update` فيحجز القفل الحصري لسطر الراوتر.
     - الطلب (ب) يستهلك رمزه، ثم يصل إلى `tx.mikroTikDevice.update` لنفس الراوتر؛ فيقوم PostgreSQL بتعليق الطلب (ب) وإدخاله في حالة انتظار (Wait Lock).
     - الطلب (أ) يلغي أي وكيل سابق، ينشئ الوكيل الجديد (Agent A)، ويُكمل المعاملة (`COMMIT`).
     - يتحرر القفل، فيستأنف الطلب (ب) تنفيذه ويحدث سطر الراوتر.
     - ينتقل الطلب (ب) إلى خطوة إلغاء الوكلاء النشطين (`tx.deviceAgent.updateMany`): بموجب مستوى العزل الافتراضي في PostgreSQL (`READ COMMITTED`)، يرى الطلب (ب) الوكيل (Agent A) الذي تم اعتماده للتو، ويقوم بإلغائه (`status = 'REVOKED'`).
     - ينشئ الطلب (ب) وكيله الجديد (Agent B) بحالة `OFFLINE` ويُكمل المعاملة.
     - **النتيجة الحتمية:** يبقى وكيل نشط واحد فقط (Agent B)، بينما يصبح (Agent A) ملغياً مع الاحتفاظ بسجله التاريخي.

2. **الخط الدفاعي الثاني: القيد الفريد الجزئي (Partial Unique Index Enforced by PostgreSQL Engine)**
   - لو افترضنا حدوث أي خلل برمجي أو سباق خارج المعاملة، فإن محرك PostgreSQL نفسه سيرفض فيزيائياً وجود سجلين لنفس `deviceId` بحيث تكون قيم `status` لكليهما تختلف عن `'REVOKED'`.
   - عند محاولة إدخال السجل الثاني المتزامن، سيرمي المحرك خطأ انتهاك قيد فريد (Unique Constraint Violation - SQLSTATE `23505` / Prisma `P2002`).

### د) حالة اختبار التكامل على PostgreSQL تجريبي
- **الفحص الفعلي للبيئة:**
  - خدمة Docker غير مثبتة على نظام التشغيل (`docker: command not found`).
  - خدمة PostgreSQL المحلية (`postgresql-x64-18`) متوقفة وتحتاج صلاحيات إدارية (Administrator Elevation).
  - قاعدة البيانات الوحيدة المهيأة في متغيرات المشروع هي قاعدة بيانات Supabase للإنتاج.
- **التزام الشفافية والامتثال:**
  - التزاماً بالشرط الصارم بعدم المساس بالإنتاج وعدم تنفيذ migrations عليها، **لم يتم تشغيل اختبار تكامل حي ضد خادم PostgreSQL تجريبي معزول**.
  - الاعتماد الحالي في الاختبارات المؤتمتة قائم على اختبارات Jest باستخدام محاكاة Prisma (`Prisma Mocks`)، مع التأكيد الهندسي النظري على صحة كود SQL وسلوك أقفال PostgreSQL المعياري.

## 2. مراجعة آلية `trust proxy` ومنع تزوير `req.ip`

### أ) الإعداد البرمجي الفعلي
1. في `apps/api/src/main.ts` (السطر 40):
   ```typescript
   (app.getHttpAdapter().getInstance() as any).set('trust proxy', 1);
   ```
2. في `apps/api/src/modules/agent/agent.controller.ts` (السطور 144-145):
   ```typescript
   const ipAddress = req.ip || req.socket.remoteAddress || '127.0.0.1';
   ```

### ب) التحليل الأمني لمنع تزوير الـ IP في مسار Render
- **مسار الاتصال الحقيقي في بيئة الإنتاج على Render:**
  $$\text{Client (Internet)} \longrightarrow \text{Render Reverse Proxy / Cloudflare (Hop 1)} \longrightarrow \text{Node.js / Express Container}$$
- **كيف يتعامل Express مع `trust proxy = 1`؟**
  - عند ضبط `trust proxy` على رقم `1`، يثق Express في قفزة بروكسي واحدة فقط (البروكسي المقابل للحاوية مباشرة).
  - عندما يرسل مهاجم ترويسة مزورة مثل:
    `X-Forwarded-For: 203.0.113.195`
    يقوم بروكسي Render بالتقاط الطلب وإضافة عنوان الـ IP الفعلي الذي اتصل بالبروكسي (مثلاً `197.25.10.5`) إلى نهاية الترويسة:
    `X-Forwarded-For: 203.0.113.195, 197.25.10.5`
  - عند وصول الطلب إلى التطبيق، يقوم Express (عبر مكتبة `proxy-addr`) بفحص الترويسة من **اليمين إلى اليسار**؛ فيأخذ القفزة الموثوقة الأولى (`197.25.10.5`) ويعتبرها `req.ip`، بينما يتجاهل تماماً كل العناوين السابقة المزورة.
- **إلغاء القراءة اليدوية غير الآمنة:**
  - تم إلغاء أي كود يقرأ `req.headers['x-forwarded-for']` يدوياً دون تنقية، والاعتماد حصراً على خاصية `req.ip` المفحوصة والمحمية بواسطة Express.
  - **الخلاصة:** لا يمكن للمهاجم تزوير الـ IP للهروب من قفل محاولات الإقران المتكررة (`rate limiting & lockout`) في بيئة نشر Render المستهدفة.

## 3. فحص بيئة التشغيل وسر الإقران (`AGENT_PAIRING_SECRET`)

### أ) هل السر مطلوب لتشغيل الـ API كله أم وحدة الوكيل فقط؟
- **فحص الكود والتبعيات:**
  1. في `apps/api/src/config/env.validation.ts`:
     المتغير مُعرف ضمن `envSchema` بقيمة افتراضية مسبقة تبدأ بـ `development_`.
  2. في `apps/api/src/modules/agent/agent.service.ts` (منشئ الخدمة Constructor):
     ```typescript
     const secret = this.configService.get<string>('AGENT_PAIRING_SECRET');
     if (!secret || secret.trim().length < 32) {
       throw new Error('FATAL: AGENT_PAIRING_SECRET missing or shorter than 32 characters...');
     }
     const nodeEnv = this.configService.get<string>('NODE_ENV', 'development');
     if (nodeEnv === 'production' && secret.toLowerCase().includes('development_')) {
       throw new Error('FATAL: Insecure development placeholder detected for AGENT_PAIRING_SECRET in production mode...');
     }
     ```
  3. في `apps/api/src/app.module.ts`:
     يتم استيراد `AgentModule` مباشرة ضمن مصفوفة `imports` الخاصة بـ `AppModule`.
- **النتيجة القطعية:**
  - لأن NestJS يقوم بتهيئة وتوليد جميع المكونات المستوردة في `AppModule` أثناء مرحلة الإقلاع (`Bootstrap`)، فإن إلقاء خطأ `FATAL` داخل منشئ `AgentService` سيؤدي إلى **انهيار عملية الإقلاع وفشل تشغيل الـ API بالكامل**، وليس مجرد تعطيل وحدة الوكيل.
  - في بيئة الإنتاج (`NODE_ENV=production`)، إذا لم يُضبط `AGENT_PAIRING_SECRET` بقيمة عشوائية آمنة لا تحتوي على البادئة التجريبية، سيفشل الخادم في بدء التشغيل نهائياً وتتوقف الخدمة عن العمل.

### ب) وضع الإعداد الفعلي في Render
- **حقيقة مؤكدة بوضوح:**
  - **لا نملك وصولاً أو أدلة فعلية على متغيرات البيئة المضبوطة داخل لوحة تحكم Render.**
  - **لا ندّعي أو نجزم بأن `AGENT_PAIRING_SECRET` مضبوط حالياً في Render.**
  - **إجراء إلزامي قبل النشر:** يجب على مسؤول النظام إدخال متغير بيئة جديد في Render Dashboard باسم `AGENT_PAIRING_SECRET` يحتوي على سلسلة عشوائية بطول لا يقل عن 32 حرفاً قبل نشر هذا التحديث على خادم الإنتاج.
