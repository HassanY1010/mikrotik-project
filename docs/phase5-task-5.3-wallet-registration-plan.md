## 1. الملخص التنفيذي

بناءً على التوجيهات والقرارات التجارية المعتمدة من صاحب المشروع، يتناول هذا التقرير هندسة وتكامل ثلاثة أركان حيوية في نموذج العمل التجاري لمنصة **SudaFi SaaS**:
1. **التسجيل الذاتي لأصحاب الشبكات (Self-Serve Registration):** إتاحة إنشاء الحسابات مباشرة عبر **تطبيق Flutter** مع حماية المنظومة من الحسابات الوهمية وتفادي منح اشتراكات مدفوعة دون استحقاق.
2. **محفظة الرصيد المستقلة (Tenant Wallet):** تمكين صاحب الشبكة من متابعة رصيده، وتقديم طلبات شحن، ومتابعة حالاتها (قيد المراجعة / مقبول / مرفوض مع السبب).
3. **اعتماد الشحن وإدارة الاشتراكات عبر المحفظة:** حصر بيع واعتماد الرصيد بيد صاحب المشروع (**Super Admin**)، وتمكين صاحب الشبكة من شراء وتجديد اشتراكات باقاته خصماً من رصيد محفظته بمعاملات مالية ذرية غير قابلة للتكرار أو التلاعب.

تم فحص الكود الفعلي لجميع طبقات المشروع (`apps/api`, `apps/mobile`, `apps/admin`, `prisma/schema.prisma`)، ويوثق هذا التقرير الواقع الفعلي القائم، الفجوات التقنية، والتصميم التنفيذي المقترح للتطبيق في المرحلة القادمة.

## 4. خطة التعديلات المطلوبة عبر مكونات النظام

### 4.1 تعديلات قاعدة البيانات (`apps/api/prisma/schema.prisma`)

1. **إضافة جدول طلبات شحن المحفظة (`WalletRechargeRequest`):**
   ```prisma
   enum RechargeRequestStatus {
     PENDING
     APPROVED
     REJECTED
   }

   model WalletRechargeRequest {
     id              String                @id @default(uuid())
     tenantId        String
     amount          Decimal               @db.Decimal(12, 2)
     currency        String                @default("SDG")
     paymentMethod   String?               // مثلاً: بنكك، فودافون كاش، إيداع نقدي
     referenceNumber String?               // رقم المعاملة أو الإشعار البنكي
     notes           String?
     status          RechargeRequestStatus @default(PENDING)
     rejectionReason String?               // سبب الرفض إن وجد
     requestedById   String
     reviewedById    String?
     reviewedAt      DateTime?
     createdAt       DateTime              @default(now())
     updatedAt       DateTime              @updatedAt

     tenant      Tenant  @relation(fields: [tenantId], references: [id], onDelete: Cascade)
     requestedBy User    @relation("RequestedBy", fields: [requestedById], references: [id])
     reviewedBy  User?   @relation("ReviewedBy", fields: [reviewedById], references: [id])

     @@index([tenantId])
     @@index([status])
     @@index([createdAt])
     @@map("wallet_recharge_requests")
   }
   ```

2. **تطوير جدول المعاملات المالية (`TenantWalletTransaction`):**
   - إضافة علاقة اختيارية مع `requestId` و `subscriptionId` لربط أي حركة مالية بمصدرها الحقيقي لضمان الشفافية وقابلية التدقيق (Auditability).

3. **تطوير جدول الاشتراكات (`Subscription`):**
   - إضافة حقل `paymentMethod` (`WALLET`, `MANUAL_ADMIN`, `FREE_TRIAL`).
   - إضافة حقل `walletTransactionId` لتوثيق رقم المعاملة المالية المخصومة.

### 4.2 تعديلات الخادم الخلفي (Backend NestJS)

1. **تحديث مسار التسجيل (`apps/api/src/modules/auth/`):**
   - تعديل `registerTenant`:
     - منع إنشاء اشتراك مدفوع تلقائياً.
     - اعتماد إما حالة `TRIAL` محددة بفترة تجريبية مع قيود مشددة على الكروت والراوترات، أو إنشاء المنشأة بدون اشتراك نشط وتوجيه صاحب الشبكة لشحن المحفظة وشراء باقة لتفعيل الربط مع الراوتر.
     - تطبيق حماية من هجمات الـ Brute-Force ومعدل الطلبات (Throttling) على مسار التسجيل لمنع إغراق السيرفر بحسابات وهمية.
2. **بناء وحدة المحفظة الجديدة (`WalletModule`):**
   - `POST /wallet/recharge-requests`: صاحب الشبكة يقدم طلب شحن (المبلغ، وسيلة التحويل، رقم العملية).
   - `GET /wallet/recharge-requests`: استعراض طلبات الشحن الخاصة بالشبكة مع حالاتها وأسباب الرفض.
   - `GET /wallet/balance`: قراءة الرصيد وسجل المعاملات المعتمدة.
3. **وحدة إدارة الشحنات لـ Super Admin (`SuperAdminModule`):**
   - `GET /admin/wallet/recharge-requests`: عرض جميع الطلبات في المنصة مع فلاتر الحالة.
   - `POST /admin/wallet/recharge-requests/:id/approve`: 
     - **تنفيذ ذري بحت داخل `$transaction`:**
       1. قفل صف الطلب والتحقق من أنه لا يزال `PENDING`.
       2. تحديث حالة الطلب إلى `APPROVED` وتوثيق هوية المدير `reviewedById` ووقت الاعتماد.
       3. زيادة رصيد محفظة المستأجر: `walletBalance = walletBalance + amount`.
       4. تسجيل حركة دائمة في `TenantWalletTransaction` بنوع `RECHARGE`.
   - `POST /admin/wallet/recharge-requests/:id/reject`:
     - التحقق من إدخال سبب الرفض (`rejectionReason`).
     - تحديث حالة الطلب إلى `REJECTED` دون إجراء أي تعديل على رصيد المحفظة.
4. **شراء وتجديد الاشتراك من المحفظة (`POST /wallet/subscriptions/purchase`):**
   - استقبال معرف الباقة `planId` والدورة `billingCycle` (شهرية / سنوية).
   - **تنفيذ ذري متزامن مع قفل الحساب:**
     1. جلب بيانات الباقة وتحديد السعر المستحق (`priceMonthly` أو `priceYearly`).
     2. قفل صف المستأجر باستخدام `SELECT ... FOR UPDATE` لمنع التزامن والخصم المكرر.
     3. التحقق الرياضي: `if (tenant.walletBalance < planPrice) throw BadRequestException('الرصيد المتاح غير كافٍ')`.
     4. خصم الرصيد: `newBalance = walletBalance - planPrice`.
     5. إنشاء معاملة خصم في `TenantWalletTransaction` بنوع `SUBSCRIPTION_PURCHASE`.
     6. تفعيل أو تمديد الاشتراك:
        - إذا كان الاشتراك منتهياً أو جديداً: يبدأ من تاريخ اللحظة الحالية.
        - إذا كان الاشتراك الحالي سارياً ويراد التجديد: يتم تمديد `expiresAt` من تاريخ الانتهاء الحالي.
     7. تحديث حالة المنشأة إلى `ACTIVE`.
   - منع أي تعديل يدوي أو حذف للمعاملات المالية لحماية نزاهة السجلات (Immutable Financial Ledger).

## 5. مصفوفة الأمان ومنع التزامن والاحتيال المالي

| المخاطرة المحتملة | السيناريو | آلية الحماية البرمجية المعتمدة في التصميم |
| :--- | :--- | :--- |
| **الإنفاق المزدوج المتزامن (Race Condition Double Spend)** | نقر المستخدم على زر شراء الاشتراك مرتين بسرعة فائقة في نفس اللحظة | استخدام قفل الصفوف `FOR UPDATE` في معاملة ذرية `$transaction` بحيث يقفل صف المستأجر حتى تكتمل المعاملة الأولى، فتفشل الثانية لعدم كفاية الرصيد. |
| **الرصيد السالب (Negative Balance)** | محاولة شراء باقة برصيد غير كافٍ عبر التلاعب بالـ API | فحص صارم ومزدوج: `WHERE id = tenantId AND walletBalance >= planPrice` قبل أي خصم. |
| **إنشاء شبكات وهمية متكررة (Spam Signups)** | روبوتات تسجل مئات الحسابات لتزاحم موارد المنظومة | تحديد معدل الطلبات (Rate Limiting) على الـ IP، اشتراط التحقق من تفرد البريد ورقم الهاتف، وعدم إعطاء اشتراكات مدفوعة تلقائياً. |
| **تعديل السجلات المالية (Ledger Tampering)** | محاولة تعديل سجل شحن قديم من واجهة المستخدم | المعاملات في جدول `tenant_wallet_transactions` تعتبر (Append-Only) ولا تتاح لها أي نقاط نهاية للحذف أو التعديل نهائياً في النظام. |
| **اعتماد مكرر لنفس الشحنة** | فتح Super Admin للطلب في نافذتين واعتماده مرتين | فحص حالة الطلب داخل القفل: إذا لم تكن الحالة `PENDING` يتم إحباط العملية فورياً برسالة `Already processed`. |

## 6. القرارات التجارية التي تحتاج إلى اعتماد نهائي من صاحب المشروع

قبل البدء في كتابة الشيفرة البرمجية، يرجى التكرم بتأكيد الخيارات التجارية التالية:

1. **سياسة الحساب الجديد بعد التسجيل الذاتي مباشرة:**
   - [ ] **الخيار 1:** يحصل على **فترة تجريبية مجانية مقيدة** (مثلاً: 14 يوماً، راوتر واحد فقط، حد أقصى 50 كرتاً) لاختبار النظام على راوتره قبل الشحن.
   - [ ] **الخيار 2:** ينشأ الحساب برصيد صفر وبدون أي اشتراك، ولا يمكنه إضافة أي راوتر أو توليد كروت إلا بعد شحن المحفظة وشراء باقة.
2. **بيانات وتعليمات التحويل المالي التي ستظهر لصاحب الشبكة:**
   - ما هي الحسابات وطرق الدفع التي ستُعرض في التطبيق ليحول العميل إليها؟ (مثلاً: رقم حساب تطبيق بنكك، محفظة فودافون كاش، أو الاتصال بالرقم المباشر).
3. **الحد الأدنى والأقصى لطلب الشحن:**
   - هل يوجد حد أدنى لشحن الرصيد في المرة الواحدة (مثلاً: 5,000 SDG أو 10,000 SDG)؟
4. **سياسة انتهاء الاشتراك:**
   - عند انتهاء أيام الباقة وعدم توفر رصيد للتجديد التلقائي:
     - هل يمنح النظام مهلة سماح (Grace Period) لمدة 3 أيام؟
     - أم يتم إيقاف توليد الكروت وأوامر الوكيل فورياً مع إبقاء الإنترنت شغالاً للمشتركين الحاليين في الراوتر؟
5. **نطاق استخدام رصيد المحفظة:**
   - هل يُستخدم رصيد المحفظة لشراء وتجديد باقات المنصة فقط، أم سيتاح مستقبلاً لشراء كروت إضافية خارج الباقة أو رسائل SMS؟

## 7. خطة الاختبارات والتحقق البرمجي المقترحة للتنفيذ

عند الانتقال إلى مرحلة التنفيذ البرمجي، سيتم بناء واختبار الحالات التالية عبر أجنحة الاختبار الآلية:

1. **اختبارات التسجيل والمصادقة (Unit & Integration Tests):**
   - نجاح تسجيل شبكة جديدة ببيانات سليمة وتشفير كلمة المرور بـ Argon2id.
   - رفض التسجيل إذا كان البريد الإلكتروني أو المعرف الفريد (slug) مستخدماً مسبقاً.
   - التأكد من عدم منح اشتراك مدفوع غير مستحق عند التسجيل.
2. **اختبارات دورة الشحن والاعتماد:**
   - إنشاء طلب شحن بحالة `PENDING`.
   - محاولة شحن بمبلغ سالب أو صفر والتأكد من رفضها.
   - قيام Super Admin باعتماد الطلب والتأكد من زيادة رصيد المحفظة وتسجيل المعاملة.
   - قيام Super Admin برفض الطلب والتحقق من بقاء الرصيد دون تغيير وظهور سبب الرفض لصاحب الشبكة.
   - محاولة اعتماد نفس الطلب مرتين للتأكد من منع التكرار.
3. **اختبارات شراء الاشتراك والتزامن:**
   - محاولة شراء باقة برصيد غير كافٍ والتأكد من الرفض.
   - نجاح الشراء وخصم الرصيد وتحديث تاريخ انتهاء الاشتراك بدقة.
   - محاولة محاكاة طلبين متزامنين في نفس الجزء من الثانية للتأكد من عمل القفل الذري ومنع الرصيد السالب.
4. **اختبارات واجهات Flutter و Web Admin:**
   - تشغيل `flutter analyze` و `flutter test` للتحقق من سلامة الواجهات.
   - تشغيل `pnpm --filter @mikrotik-saas/admin build` للتحقق من سلامة شاشات Super Admin.
